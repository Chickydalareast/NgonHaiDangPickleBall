## Part A contract

### Service points

- V1 seed ensures ten active courts: `san-01` through `san-10`.
- Seeding is additive and does not overwrite admin edits to existing service points.
- Admin APIs can list, create and update service points.
- Service point slugs are immutable after creation because printed QR codes depend on them.
- Name, code, status and sort order remain editable.
- Deactivation is blocked while the court has an open bill or a pending staff request.
- Inactive courts remain visible to admin but public context and ordering reject them.

### QR assets

- QR payload is derived from `WEB_ORIGIN` and the immutable service point slug.
- Canonical payload format: `{WEB_ORIGIN}/s/{slug}`.
- Admin can download one SVG, one PNG or one ZIP containing all active courts.
- The ZIP includes `manifest.json`, `svg/*.svg` and `png/*.png`.
- PNG verification decodes the generated QR and compares the payload with the canonical customer URL.
- QR binaries are derived artifacts and are not stored in PostgreSQL.
- `artifacts/` is ignored by Git.

### Production printing rule

Local exports intentionally point to the current `WEB_ORIGIN`, commonly `http://localhost:8080`. QR files for physical printing must be regenerated after the production domain is configured in Step 11.

## Part B contract

### Read model, not accounting mutation

- Original `orders` and `order_lines` remain unchanged and auditable.
- Provisional bill items are derived at read time; equivalent snapshots across multiple orders are grouped for display only.
- Grouping requires the same line kind, catalog item, item-name snapshot, unit-name snapshot and unit-price snapshot.
- Price changes create a separate summary row; historical snapshots are never rewritten.
- Voided lines and cancelled orders are excluded from financial summary totals but remain visible in order history.
- Reads run in repeatable-read, read-only transactions to avoid mixed snapshots while orders are changing.

### Settlement-ready totals

Part B introduces the stable projection shape required by Parts C and D:

- `grossTotalVnd`
- `paidTotalVnd`
- `waivedTotalVnd`
- `outstandingTotalVnd`
- equivalent quantity fields for each summary row

Before settlement is implemented, paid and waived values are zero and outstanding equals gross.

### Customer tracking

```text
GET /api/public/service-points/:slug/bill
```

- Returns HTTP 200 with `bill: null`, empty orders and a zero summary when an active court has no open bill.
- Returns the current open bill, sanitized order history and grouped provisional summary when a bill exists.
- Does not expose order notes, cancellation reasons, void reasons or admin identity.
- Uses `Cache-Control: no-store` and is designed for customer polling.
- Inactive or unknown service points return typed HTTP 404.

### Admin bill extension

`GET /api/admin/bills/:billId` now includes the same projection summary plus `bill.updatedAt`. Admin and customer summaries are generated by one shared projection function.

## Part C contract

### Admin-only custom charges

Custom charges are transactional bill lines created by an authenticated admin. They are not catalog records and never appear in the customer ordering menu.

```text
POST  /api/admin/bills/:billId/custom-charges
PATCH /api/admin/custom-charges/:chargeId
POST  /api/admin/custom-charges/:chargeId/void
```

### Manual product charge

`MANUAL_PRODUCT` stores immutable financial snapshots for a product or fee that is not in the public catalog:

- custom name and unit name;
- integer quantity;
- integer VND unit price;
- server-calculated line total;
- `catalogItemId = null`.

### Manual time charge

`MANUAL_TIME` accepts:

- custom name;
- actual duration in minutes;
- billing interval in minutes;
- integer VND price per interval.

The server calculates `billableIntervals = ceil(durationMinutes / billingIntervalMinutes)`. The order-line quantity stores those billable intervals, while actual duration and billing interval are retained separately for audit and display.

### Correctness rules

- Creation requires an idempotency UUID. A replay with the same payload returns the existing result without another line or activity log.
- Reusing an idempotency UUID with different financial data is rejected.
- Custom charge type is immutable after creation.
- Editing is allowed only while the line is active and its admin order is pending or accepted.
- Voiding requires a reason and never hard-deletes the order line.
- Every mutation uses the existing bill advisory lock, recalculates server-owned order and bill totals, writes an activity log and publishes `bill.updated` after commit.
- Customer and admin bill projections expose the same manual lines and totals.
- Manual lines have no catalog item or image snapshot.

### Migration

Part C adds the `order_line_kind` enum and nullable custom-charge metadata to `order_lines`. Existing rows are migrated as `CATALOG`, preserving all prior data and behavior.

## Part D contract

### Quantity-based settlement allocation

An authenticated admin can allocate an active order line by quantity rather than by an arbitrary money amount:

```text
POST /api/admin/order-lines/:lineId/settlements
POST /api/admin/settlements/:settlementId/reverse
```

Supported allocation types:

- `PAID`: quantity that has been paid;
- `WAIVED`: quantity that is intentionally not collected and requires a reason.

The server copies the order-line unit-price snapshot and calculates `amountVnd = quantity × unitPriceVnd`. Clients cannot submit an amount or change historical prices.

### Partial and grouped projection

- Multiple active allocations can target one order line until its full quantity is allocated.
- Active paid plus waived quantity can never exceed the order-line quantity.
- Reversed allocations remain stored for audit but no longer contribute to paid or waived totals.
- Admin and public bill readers use one settlement-state calculator and one grouped bill projection.
- Every order line and grouped projection item exposes paid, waived and outstanding quantities and VND totals.

### Mutation protection

While an order line has at least one active settlement:

- its quantity and financial snapshot cannot be edited;
- it cannot be voided;
- its parent order cannot be cancelled;
- custom product/time charges cannot be edited or voided.

After all active settlements are reversed, the normal pre-service edit and void rules apply again.

### Reversal and audit

- Settlement creation and reversal both require idempotency UUIDs.
- Exact replays return the existing result without duplicate financial rows or activity logs.
- Reusing a key for another payload or settlement is rejected.
- A reversal requires a reason and records the reversing admin and timestamp.
- Rows are never hard-deleted; reversal changes status from `ACTIVE` to `REVERSED`.
- Each committed create or reversal writes an activity log and publishes `bill.updated` best-effort after commit.

### Bill completion rule

A bill can be completed only when:

- no order remains `PENDING` or `ACCEPTED`; and
- every active order-line quantity is fully classified as `PAID` or `WAIVED`.

The completed bill total remains the gross server-calculated bill total. Paid and waived values remain an operational settlement projection, not accounting or payment-gateway records.

### Migration

Part D adds `settlement_type`, `settlement_status` and the `order_line_settlements` audit table. Migration journal timestamps remain strictly increasing through `0003_partial_settlements`.

## Part E contract

### Transaction-scoped read hardening

Admin and public bill snapshots run inside repeatable-read transactions. PostgreSQL `PoolClient` instances now execute the order, line and settlement queries sequentially. This preserves one consistent snapshot without relying on the deprecated node-postgres behavior that queued overlapping `client.query()` calls on the same connection.

### Concurrency acceptance

The completion verifier proves the bill advisory lock remains the single serialization boundary for operational financial mutations:

- two competing allocations cannot over-allocate one line;
- concurrent exact idempotent replays create one settlement row;
- settlement reversal racing bill completion cannot make both operations succeed;
- the losing operation receives the correct domain conflict after it acquires the lock;
- the final bill can still reach a consistent completed state.

### Migration integrity

`pnpm migrations:verify` checks the Drizzle journal before every quality gate:

- contiguous migration indexes and filename prefixes;
- unique migration tags;
- strictly increasing safe-integer timestamps;
- one SQL file and one snapshot for every journal entry;
- no unjournaled SQL migration or orphaned snapshot.

This prevents an existing database from silently skipping a migration whose journal timestamp is older than the previously applied migration.

### Consolidated verification

The first round covers static quality and migration metadata. The second runs isolated-database behavior and concurrency checks. The third runs Docker-backed HTTP integration and all V1 regressions.
